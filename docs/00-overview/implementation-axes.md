# 구현 축 6가지

디자인 시스템의 모든 단위는 **동일한 6개 축**으로 판정합니다.
축이 고정되어 있기 때문에 서로 다른 영역(Token / Component / Layout …)의 진행 상태를 같은 기준으로 비교할 수 있습니다.

빈칸은 그대로 **할 일 목록**입니다.

---

## 1. 원칙 설계 (Principle)

**질문**: 이 단위가 **무엇을 책임지고, 무엇을 책임지지 않는가**가 정의되어 있는가?

- [ ] 이 단위의 존재 이유가 한 문장으로 적혀 있다
- [ ] 계층·구조(몇 단, 어떤 슬롯)가 확정되어 있다
- [ ] **책임 경계**가 있다 — 이 단위가 다루지 **않는** 것이 명시되어 있다
- [ ] 상·하위 단위와의 관계(참조 방향)가 정의되어 있다

> 예: "Semantic은 의도만 담는다. State는 Semantic의 책임이 아니다" ← 책임 경계

---

## 2. 네이밍 규칙 (Naming)

**질문**: 두 사람이 각자 이름 붙였을 때 **같은 이름**이 나오는가?

- [ ] 세그먼트 문법이 확정 (`Target/Role/Variant` 형태)
- [ ] 각 슬롯에 들어갈 수 있는 값이 **닫힌 집합**(enum)으로 나열 — "등", "기타" 없음
- [ ] 표기 규칙(대소문자, 띄어쓰기, 구분자) 확정
- [ ] 계층 간 **어휘가 통일**되어 있다 (같은 개념 = 같은 단어)
- [ ] 예외 표기(`_` 접두사 등)가 규칙의 일부로 정의됨

---

## 3. 사용 규칙 (Usage)

**질문**: **언제 무엇을 고르는지**, 그리고 **무엇이 금지인지**가 적혀 있는가?

- [ ] 선택 기준 — 비슷한 후보 중 하나를 고르는 규칙
- [ ] 금지 사항 — 하면 안 되는 것과 그 이유
- [ ] 잘못된 사용 예시와 올바른 형태 (Do / Don't)
- [ ] 다른 영역과 충돌할 때의 우선순위

> 규칙이 "권장"으로만 적혀 있으면 이 축은 미완입니다. 금지가 없으면 판별할 것도 없습니다.

---

## 4. 확장 규칙 (Extension)

**질문**: **새 항목을 추가할 때** 밟아야 할 절차가 있는가?

- [ ] 추가 절차 — 누가, 어디에, 어떤 형식으로
- [ ] 승인 기준 — 무엇을 만족해야 추가가 허용되는가
- [ ] 변경 시 영향 범위 확인 방법
- [ ] 폐기(deprecation) 절차

---

## 5. 판별 테스트 (Test)

**질문**: 위반인지 아닌지를 **예/아니오로** 가를 수 있는가?

- [ ] 질문 세트가 존재한다 (산문 설명이 아니라 질문 형태)
- [ ] 각 질문이 **단일 판정**을 내린다 — 해석의 여지가 없음
- [ ] 중복 없이 **단일본**으로 존재한다
- [ ] 규칙 ID가 부여되어 있다 (게이트웨이가 참조할 대상)

> **이 축이 이 대시보드의 핵심입니다.** 판별 테스트가 없는 규칙은 문서일 뿐 시스템이 아닙니다.
> AI Readable = 설명 없이 구조만으로 판정 가능한 상태이므로, 이 축이 곧 AI Readable 여부입니다.

---

## 6. 코드 동기화 (Sync)

**질문**: 기계가 읽는 형태로 **실제로 존재하고, 실제로 맞춰지는가**?

- [ ] machine-readable 형식(JSON / 스키마 / 코드)으로 존재
- [ ] 디자인 ↔ 코드 간 동기화 경로가 있다 (수동이어도 경로가 정의되어 있으면 부분 인정)
- [ ] 동기화 방향이 정해져 있다 (단방향 / 양방향 / 어느 쪽이 원본인가)
- [ ] 어긋났을 때 감지되는가

---

## 판정 기호

| 기호 | 의미 |
|:---:|---|
| ✅ | 위 체크 항목이 **전부** 충족됨 |
| 🟡 | 일부만 충족 — 문서는 있으나 구멍이 있음 |
| ⬜ | 미착수 |
| — | 이 단위에는 해당 축이 적용되지 않음 (진행률 계산에서 제외) |

> ⚠️ **"문서를 썼다"는 ✅가 아닙니다.** 각 축의 체크 항목을 실제로 만족해야 ✅입니다.
> 특히 네이밍 축은 enum이 하나라도 열려 있으면 🟡을 넘지 못합니다.
