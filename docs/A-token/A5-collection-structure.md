# A5. 컬렉션 구조 · 참조 · Mode

> 담당: **컬렉션들 사이의 관계**. 개별 티어가 아니라 티어 간 규칙을 다룬다.
> A1~A4가 각 층의 규칙이라면, A5는 **층 사이의 규칙**이다.

| 원칙 설계 | 네이밍 규칙 | 사용 규칙 | 확장 규칙 | 판별 테스트 | 코드 동기화 |
|:---:|:---:|:---:|:---:|:---:|:---:|
| ✅ | — | 🟡 | ⬜ | ⬜ | ⬜ |

> 네이밍 축은 A5에 해당하지 않습니다 (개별 토큰 이름은 A1~A4의 책임).

---

## 1. 원칙 설계 — ✅

- [x] **4컬렉션 구조**: Foundation / Semantic-Theme / Semantic-Responsive / Component
- [x] **3단 위계**: Foundation → Semantic → Component
- [x] **단방향 참조** — 역방향·동일 티어 간 참조 금지
- [x] Semantic을 Theme·Responsive 두 컬렉션으로 분리

## 2. 네이밍 규칙 — 해당 없음

## 3. 사용 규칙 — 🟡

- [x] 티어 건너뛰기 금지 (Component가 Foundation을 직접 참조하지 않는다)
- [ ] ⚠️ **Duration · Easing · Shadow의 Semantic 부재로 인한 참조 데드락**
      → Component가 참조할 Semantic이 없어 규칙상 Foundation 직접 참조가 불가피한 상태.
        Semantic을 만들 것인가, 예외를 인정할 것인가 → **미결**
- [ ] Mode 축의 정의 — 어느 컬렉션이 어떤 Mode를 갖는가
      - Theme: Light / Dark / …?
      - Responsive: Breakpoint / Density?
- [ ] Mode 간 값이 없을 때의 fallback 규칙
- [ ] 컬렉션 간 값이 어긋났을 때의 우선순위

## 4. 확장 규칙 — ⬜

- [ ] **새 컬렉션을 여는 조건** — 다섯 번째 컬렉션이 필요해질 때의 판단 기준
- [ ] 새 Mode 추가 시 전 컬렉션 파급 확인 절차
- [ ] 티어 간 규칙 변경 시 승인 절차 (영향 범위가 가장 큼)
- [ ] 승인자 지정

## 5. 판별 테스트 — ⬜

```
Q1. 이 참조가 단방향(하위 → 상위) 인가?
Q2. 티어를 건너뛴 참조인가?                    → 맞으면 위반
Q3. 같은 티어 안에서 참조하고 있는가?           → 맞으면 위반
Q4. 순환 참조가 존재하는가?
Q5. 참조 대상이 없는(dangling) 토큰이 있는가?
Q6. Mode가 정의된 컬렉션에서 값이 비어 있는 Mode가 있는가?
```

- [ ] 위 질문 세트 확정 + 규칙 ID 부여
