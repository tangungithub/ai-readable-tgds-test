# E. Design–Code 연결

> 담당: **디자인 자산과 코드 자산의 대응 관계**
> 목표: AI가 디자인을 보고 코드를 **추론하지 않는다**

Figma의 **Code Connect**는 E1의 구현 수단, **Variable REST API**는 E2, **Dev Mode MCP**는 E3의 구현 수단입니다.

> 이 영역은 "일관성의 지속성"이 실제로 발생하는 지점입니다.
> A~D가 아무리 잘 정의돼도 여기가 비어 있으면 규칙은 디자인 파일 안에서만 유효합니다.

## E1. 컴포넌트 매핑 (Code Connect)

**원칙 설계**
- [ ] 매핑 대상 범위 — 전 컴포넌트인가, 층(B1) 기준으로 일부인가
- [ ] 플랫폼 범위 — Web / iOS / Android 중 어디까지
- [ ] **매핑 정의의 소재지** — DS 레포인가, 각 플랫폼 레포인가 ⚠️
- [ ] 1:N 대응 처리 (한 디자인 컴포넌트에 플랫폼별 구현이 여럿일 때)

**네이밍 규칙**
- [ ] Figma 컴포넌트 이름(D2) ↔ 코드 컴포넌트 이름의 변환 규칙
- [ ] B2 Property/Variant ↔ 코드 prop 이름 대응 표기법

**사용 규칙**
- [ ] 매핑 대상 우선순위 — 사용 빈도 / detach 빈도 중 무엇 기준인가
- [ ] 미매핑 컴포넌트의 표시·추적 방법
- [ ] 코드가 먼저 바뀐 경우 매핑 갱신 **책임자** ⚠️

**확장 규칙 / 판별 테스트 / 코드 동기화**
- [ ] 신규 컴포넌트의 매핑 등록을 필수로 할 것인가
- [ ] 판별 질문 세트 (예: "이 컴포넌트에 매핑이 존재하는가?", "매핑된 코드가 실재하는가?")
- [ ] 매핑 누락을 게이트웨이(F2)에서 검출할 것인가

## E2. 토큰 동기화 파이프라인

**원칙 설계 — 🟡**
- [x] **동기화 방향** — 등록부(`token/*.json`)가 원본, **코드 → Figma 단방향** ([E2](E2-token-sync.md) 작업 2). Figma 손수정은 다음 동기화에 덮인다
      *참고: zeroheight 2026 설문에서 양방향 동기화를 구현한 조직은 5%*
- [ ] 동기화 단위 (컬렉션별? 전체?)
- [ ] 동기화 주기 (수동 / PR 시 / 스케줄)

**사용 규칙 — 🟡**
- [x] **codeSyntax 변환 규칙** — `TKN-04` (세그먼트 경계 중첩, 내부 camelCase)
- [x] 코드 측 직접 수정 — 등록부 json이 유일한 수정 지점. 생성물 `src/tokens/*`는 손으로 고치지 않는다 (`TKN-03`·`FND-12`)
- [x] 충돌 시 우선순위 — 등록부가 정본 (`TKN-03`)
- [ ] 실행 시점 — 수동 / pre-commit / CI

**확장 규칙 / 판별 테스트 / 코드 동기화**
- [ ] 새 컬렉션 추가 시 파이프라인 확장 절차
- [ ] 판별 질문 세트 (예: "Figma 토큰과 코드 토큰의 집합이 일치하는가?")
- [ ] JSON 스키마 확정
- [ ] **어긋남 감지** — drift를 어떻게 알아채는가

## E3. 도구 · AI 접근 경로

> AI가 디자인 시스템을 읽는 **실제 경로**. 이것이 없으면 A~D의 규칙은 AI에게 도달하지 않습니다.

**원칙 설계**
- [ ] Dev Mode MCP 연동 범위
- [ ] AI에게 노출할 것 / 노출하지 않을 것
- [ ] 규칙 문서를 AI가 읽는 형식으로 어떻게 제공하는가 (이 저장소인가, 별도 스키마인가) ⚠️

**사용 규칙 / 확장 규칙 / 판별 테스트 / 코드 동기화**
- [ ] AI 작업 시 참조해야 할 문서의 우선순위
- [ ] 새 규칙이 추가됐을 때 AI 컨텍스트에 반영하는 절차
- [ ] **AI 판별 테스트** — AI에게 규칙만 주고 신규 토큰·컴포넌트를 만들게 했을 때 통과하는가 ⚠️
      → 이것이 이 프로젝트 전체의 최종 검수 방법
- [ ] machine-readable 규칙 병행본의 형식

---

> ⚠️ E2·E3의 **네이밍 규칙 축**은 해당 없음(—)으로 둡니다. 파이프라인·경로에는 식별자 문법이 없습니다.
