# B. Component 아키텍처

> 담당: **컴포넌트가 무엇으로 이루어지고, 어디까지 변형될 수 있는가**
> 목표: AI가 컴포넌트를 보고 **허용된 변형의 범위**를 추측 없이 판별한다

Figma의 **Auto Layout**은 B4의 구현 수단, **Slot**은 B5의 구현 수단입니다. 기능이 아니라 원칙이 판정 대상입니다.

## B1. 컴포넌트 분류 체계

> 컴포넌트를 어떤 층으로 나누는가. 이것이 없으면 A4 Component Token의 첫 세그먼트 기준 집합도 없다.

**원칙 설계**
- [ ] 층 정의 — Primitive / Composite / Pattern / Template 등 몇 층으로 나누는가
- [ ] 각 층의 책임 경계 — 어느 층이 토큰을 직접 바인딩하는가
- [ ] 층 간 조합 방향 (하위 층만 조합 가능한가)
- [ ] 라이브러리 분리 여부 (→ [D3](../D-naming/README.md))

**네이밍 규칙**
- [ ] 컴포넌트 이름 문법 (→ [D2](../D-naming/README.md)와 단일본 공유)
- [ ] 층을 이름으로 드러낼 것인가

**사용 규칙 / 확장 규칙 / 판별 테스트 / 코드 동기화**
- [ ] 어느 층에 만들지 결정하는 기준
- [ ] 신규 컴포넌트 추가 절차 — `DENY-03`(DS 외부 제작 커밋)의 정당한 대안 경로
- [ ] 판별 질문 세트
- [ ] 코드 컴포넌트와의 층 대응

## B2. Property · Variant 모델

> 하나의 컴포넌트가 갖는 변형 축의 구조. A4 Component Token의 `Variant` 슬롯이 여기서 나온다.

**원칙 설계**
- [ ] 변형 축의 종류 정의 — 시각 변형(Primary/Secondary) / 크기(Size) / 형태(Shape) …
- [ ] 축 개수 상한 — 조합 폭발을 어디서 막는가
- [ ] Boolean property vs Variant 선택 기준
- [ ] Instance swap property를 쓰는 경우 (→ B5와 경계 정리)

**네이밍 규칙**
- [ ] Property 이름 문법
- [ ] Variant 값의 닫힌 집합 — 컴포넌트별 enum을 어디에 정의하는가
- [ ] A4 Component Token의 `Variant` 슬롯과 **같은 값을 쓸 것을 강제**할 것인가 ⚠️

**사용 규칙 / 확장 규칙 / 판별 테스트 / 코드 동기화**
- [ ] 축을 늘리기 전 검토 순서
- [ ] 신규 Variant 추가 시 토큰 파급 확인
- [ ] 판별 질문 세트
- [ ] 코드 prop과의 대응 (→ [E1](../E-design-code/README.md))

## B3. State 모델

> State가 표현되는 유일한 티어는 A4 Component Token. 그렇다면 State의 **목록과 의미**는 여기서 정의되어야 한다.

**원칙 설계 — 🟡**
- [x] State는 Semantic이 아니라 **Component 티어에서만** 표현한다 (A2 책임 경계에서 확정)
- [ ] ⚠️ **State의 닫힌 목록** — Default / Hover / Pressed / Focused / Disabled / Selected / Loading / Error …?
      → 이 목록이 없어서 A4 판별 테스트 Q3을 만들 수 없음
- [ ] 각 State의 정의 — 언제 이 상태인가
- [ ] 조합 State 허용 여부 (Hover + Selected)
- [ ] 플랫폼별 차이 (Hover가 없는 터치 환경)

**나머지 축**
- [ ] State 이름 표기 규칙
- [ ] 어떤 컴포넌트에 어떤 State가 **필수**인가
- [ ] 신규 State 추가 시 전 컴포넌트 파급 확인 절차
- [ ] 판별 질문 세트
- [ ] 코드의 상태 표현과의 대응

## B4. 구조 · 조합 규칙

> 컴포넌트 내부가 어떻게 구성되는가. **Auto Layout이 이 원칙의 구현 수단.**

**원칙 설계**
- [ ] 내부 구조의 표준형 — 어떤 레이어 구성을 갖는가
- [ ] 중첩 깊이 상한
- [ ] 절대 위치를 허용하는 경우의 목록 (오버레이, 장식 등)
- [ ] Hug / Fill / Fixed 선택 기준

**네이밍 규칙**
- [ ] 내부 레이어 네이밍 (→ [D1](../D-naming/README.md))

**사용 규칙**
- [ ] ⚠️ Auto Layout **필수 적용 범위** — 전 컴포넌트인가, 어떤 조건 이상인가
- [ ] gap·padding을 [A3 Responsive 토큰](../A-token/A3-semantic-responsive.md)에 바인딩하는 것을 강제할 것인가
- [ ] 하드코딩 수치 허용 예외

**확장 규칙 / 판별 테스트 / 코드 동기화**
- [ ] 구조 변경 시 인스턴스 영향 확인 절차
- [ ] 판별 질문 세트 (예: "이 프레임에 Auto Layout이 없는데 예외 목록에 있는가?")
- [ ] 코드의 레이아웃 구현과의 대응

## B5. 유연성 · 변형 수용

> **Slot이 이 원칙의 구현 수단.** 목표는 detach 금지가 아니라 **detach가 필요 없게 만드는 것**.

**원칙 설계 — 🟡**
- [x] Input류는 Element 슬롯 **필요**, Button류는 **불필요** (사례 2건 확정)
- [ ] ⚠️ **위 사례를 일반 규칙으로 승격** — 어떤 조건의 컴포넌트에 슬롯을 두는가
- [ ] 슬롯 남용 방지선 — 모든 것이 슬롯이면 시스템이 아님
- [ ] 슬롯 vs Variant 추가 vs 별도 컴포넌트: 선택 기준

**네이밍 규칙**
- [ ] 슬롯 프레임 이름 문법 — [D1 Frame Naming](../D-naming/README.md) 규칙을 따르는가, 별도인가

**사용 규칙**
- [ ] 슬롯에 넣을 수 있는 것 / 없는 것
- [ ] 슬롯 내부 요소의 토큰 바인딩 강제 여부
- [ ] Detach 금지 정책 — 전면 금지인가, 조건부인가

**확장 규칙 / 판별 테스트 / 코드 동기화**
- [ ] **Detach 다발 컴포넌트 역추적** → 슬롯 후보 도출 절차
      *근거: Deliveroo에서 최다 detach 컴포넌트 8개 중 7개가 multi-line text 포함 — detach는 유연성 결핍 신호*
- [ ] 슬롯 추가 시 기존 인스턴스 영향 확인
- [ ] 판별 질문 세트
- [ ] 코드의 children / composition 패턴과의 대응

→ [근거 리서치](../99-reference/research.md)
